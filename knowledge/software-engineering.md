# 软件工程技术知识库

## 软件工程是什么

软件工程是应用系统化、规范化的方法进行软件的开发、运行和维护的学科。

软件工程的核心目标是在规定的时间和成本内，交付满足需求的高质量软件。

## 软件生命周期

软件生命周期包括以下阶段：

1. 问题定义与可行性分析
2. 需求分析
3. 概要设计与详细设计
4. 编码实现
5. 测试
6. 运行与维护

其中维护阶段占软件生命周期成本的比例最高。

## 瀑布模型

瀑布模型将软件开发过程按固定顺序划分为线性阶段，上一阶段完成后才进入下一阶段。

瀑布模型的优点是流程清晰、文档完整、便于管理，缺点是难以应对需求变化，问题往往在后期才暴露。

适合需求明确、技术成熟、周期较长的项目。

## 敏捷开发

敏捷开发强调以人为本、快速迭代、拥抱变化。

敏捷宣言的核心价值观包括：个体和互动高于流程和工具、可工作的软件高于详尽的文档、客户合作高于合同谈判、响应变化高于遵循计划。

Scrum 是最常用的敏捷框架，通过短周期 Sprint 交付可用的软件增量。

## 需求工程

需求工程包括需求获取、需求分析、需求规格说明和需求验证四个活动。

需求分为功能需求和非功能需求：功能需求描述系统应该做什么，非功能需求描述质量属性，例如性能、安全、可用性、可扩展性。

需求变更不可避免，关键是通过需求基线和变更控制流程管理变更。

## 高内聚低耦合

高内聚指一个模块内部的元素紧密相关，共同完成单一职责。

低耦合指模块之间的依赖尽量少、接口尽量简单。

高内聚低耦合的系统可读性好、易于测试、修改某模块时不容易影响其他模块，是软件设计最基本的原则之一。

## SOLID 原则

SOLID 是面向对象设计的五大原则：

1. 单一职责原则，一个类只负责一件事；
2. 开闭原则，对扩展开放，对修改关闭；
3. 里氏替换原则，子类必须能够替换父类；
4. 接口隔离原则，接口尽量小而专一；
5. 依赖倒置原则，依赖抽象而不依赖具体实现。

## 设计模式

设计模式是针对常见问题的可复用解决方案，通常分为三类：

1. 创建型模式，例如单例、工厂、建造者；
2. 结构型模式，例如适配器、装饰器、代理；
3. 行为型模式，例如策略、观察者、模板方法。

单例模式保证一个类只有一个实例；策略模式用组合替代条件分支；观察者模式实现一对多的事件通知。

## 软件测试

软件测试按阶段分为：

1. 单元测试，验证最小可测单元；
2. 集成测试，验证模块之间协作；
3. 系统测试，验证整个系统满足需求；
4. 验收测试，由用户确认交付。

按对代码的可见程度分为黑盒测试和白盒测试。

测试左移强调尽早介入测试，测试右移强调在生产环境持续监控。

## 单元测试

单元测试是针对类或方法级别的自动化测试，常用 JUnit 和 Mockito。

好的单元测试具有以下特点：运行快、可重复、自验证、相互独立。

Mock 用于隔离被测对象的外部依赖，只验证当前单元的逻辑。

测试覆盖率是衡量测试充分性的指标，但高覆盖率不等于高质量测试。

## 版本控制

版本控制用于管理代码的修改历史，支持多人协作和版本回溯。

Git 的核心概念：工作区、暂存区、本地仓库、远程仓库。

常见分支策略：主分支保持可发布，功能分支开发新特性，通过合并请求合入主干并触发流水线。

## CI/CD

CI 持续集成指代码提交后自动构建、自动测试，尽早发现集成问题。

CD 可以指持续交付，即随时可以发布；也可以指持续部署，即自动发布到生产环境。

CI/CD 流水线的典型阶段：编译构建、静态检查、单元测试、打包、部署、冒烟测试。

## 代码评审

代码评审是在代码合入主干前由他人检查代码的活动。

评审关注点包括：正确性、可读性、命名、边界条件、安全隐患、测试完整性。

代码评审的价值不只是发现缺陷，还包括知识共享和风格统一。

## 重构

重构是在不改变软件外部行为的前提下，改善代码内部结构。

常见重构手法：提取方法、提取变量、内联函数、以多态取代条件表达式、提炼类。

重构应该小步进行，每一步都有测试保护。

## 微服务架构

微服务架构将系统拆分为一组小型、自治的服务，每个服务独立开发、独立部署、独立扩容。

微服务带来的新问题需要配套方案：服务注册与发现、配置中心、API 网关、链路追踪、分布式事务。

服务拆分通常按照业务能力进行，避免拆分过细导致分布式单体。

## 单体架构与微服务对比

单体架构的优点：开发部署简单、事务一致性好、调用没有网络开销。

单体架构的缺点：代码膨胀后维护困难、只能整体扩容、单点故障影响全局。

微服务适合业务复杂、团队规模大、需要独立伸缩的场景；小团队和小项目从单体起步往往更合适。

## 分布式事务

分布式事务的常见方案：

1. 两阶段提交，强一致但性能差、有阻塞风险；
2. TCC，Try-Confirm-Cancel 三阶段，业务侵入大但灵活；
3. 本地消息表，基于最终一致性的可靠消息方案；
4. Saga 模式，长事务拆分为多个本地事务，失败时执行补偿。

大多数互联网业务选择最终一致性而不是强一致性。
